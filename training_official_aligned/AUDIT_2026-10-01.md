# Training-entry audit — 1 October 2026

This review covers the independent `training_official_aligned` entry and its data/diagnostic helpers. The original training entry, shared model implementation and Gadi recovery scripts were not edited. This is a fresh-training protocol for the existing 121-channel DIEPformer, not a reproduction of the official DIEP architecture and not an Adam causality experiment.

## What the diagnostics answer

| Evidence | Practical question |
|---|---|
| Train/validation E/F/S MAE, RMSE, Huber and learning rate | When did deterioration start, which target changed, and did it persist into validation? |
| Batch source-row IDs, atom/edge/triplet counts and per-structure errors | Is the error concentrated in particular structures or associated with unusually complex batches? |
| Pre/post-clipping gradients and actual parameter changes | Was clipping active, and how large was the optimizer's actual step? |
| AdamW moments, AMSGrad denominator and 128 fixed scalar probes | Is there evidence of a mismatch between recent gradients and the adaptive scale? |
| Per-module parameter, gradient, moment and update summaries | Which parameter groups first show unusual gradients or updates? |
| Per-rank CUDA allocator statistics and host elapsed time | Are workload, memory and timing imbalanced or correlated with anomalies? |
| Source/data identities, split membership, full epoch checkpoints | Which exact setup produced the observation, and can training continue from a known boundary? |

These measurements support diagnosis; correlations alone do not establish cause. The observer does not retain all gradients, activations or Hessians. The fixed probes are parameter coordinates, not structures. Host elapsed time is not GPU kernel timing.

## Findings and corrections

1. **One scheduler owner.** The new module registers one epoch-based cosine scheduler with Lightning and never manually steps it. It does not inherit the original training module's epoch hooks.
2. **Partial-epoch recovery was unsafe.** A rolling snapshot restored inside an epoch skipped initialization of the phase accumulator and failed with `KeyError('train')`. Partial-epoch training resume is now explicitly refused. Rolling snapshots remain useful for diagnosis; normal continuation uses the latest completed-epoch `last.ckpt`. The final training-batch snapshot, before validation/epoch saving, is also diagnostic-only.
3. **Invalid stopping limits are rejected.** A checkpoint with 200 completed epochs cannot silently be resumed with a stopping limit of 199. Resuming the completed campaign at its proper limit makes no additional optimizer/scheduler updates.
4. **Failure evidence is retained.** Before rejecting nonfinite loss, the entry records the failing batch's errors. Pending scalar, module and coordinate information survives a nonfinite-gradient stop. Logging errors do not replace the original training exception.
5. **Distributed rejection is coordinated.** Nonfinite train/validation/test losses and gradients cause all ranks to stop before the corresponding optimizer update, rather than leaving another rank waiting at metric reduction.
6. **One invocation owns each output directory.** A lifetime lock and fresh launch identity reject concurrent fresh/resume jobs. Lightning children and standard single-node torchrun workers join the verified parent launch; static torchrun IDs and stale descriptors do not bypass ownership.
7. **Cached content is checked.** SHA256 verification now includes cached labels, graphs, lattices and state data, so a same-size cache modification cannot silently reuse the recorded identity.
8. **Environment metadata is portable.** Version recording supports a `pymatgen-core` installation without requiring the optional `pymatgen` umbrella distribution.

The underlying E/F/S objective, optimizer settings, atom-budget sampler, model and clipping threshold were not changed by this audit.

## Validation

| Check | Result and scope |
|---|---|
| Actual Lightning 200-epoch schedule | 400 optimizer updates, exactly 200 scheduler advances. Initial LR 0.001; after 100 epochs 0.000505; after 200 epochs 0.00001. A tiny synthetic E/F/S predictor accelerates this control-flow test. |
| Interruption after 73 completed epochs | Resumed LR trace, final weights, AdamW/AMSGrad tensors and scheduler state exactly match the uninterrupted campaign. |
| Checkpoint boundaries | Epoch/best saves contain the next epoch's scheduler state; an earlier validation-best model remains selected when later validation worsens; unsafe partial-epoch resume is explicitly rejected. |
| Real MatPES integration | 24 real structures: fresh E/F/S fit, completed-epoch resume, explicit validation-best final test and full Potential export. Exported weights, references and scale match the selected checkpoint. |
| Observer noninterference | Real-model CPU and toy CPU/GPU comparisons retain exactly equal parameters and optimizer states with logging on/off. |
| Full entry on available hardware | One RTX4060 GPU and two CPU Gloo processes complete fit, validation, best-checkpoint test and export. |
| DDP weighting | A real E/F/S two-rank update matches sequential averaging of the same unequal microbatches, including gradient clipping and optimizer states. |
| Metrics and data | Pooled metrics are invariant to evaluation packing; padding contributes zero validation/test weight; RMS uses training atoms only; stress conversion occurs once; splits/reference coverage are checked. |
| Failure injection | One-rank nonfinite validation/test loss and gradients stop both Gloo ranks without an optimizer update and preserve diagnostics. |
| Ownership and cache tests | Duplicate/stale launch rejection, valid worker admission, lock cleanup and same-size cache tampering checks pass. |

Reproducible checks are under `测试笔记本/official_aligned_training_20260930/`. Pure synthetic tests need no MatPES download. Real-data tests require the local 24-structure fixture and MatPES reference file described in that directory's README. Large datasets, checkpoints and generated logs are not part of this source delivery.

## Operational boundaries

- Use `checkpoints/last.ckpt` for ordinary continuation, keeping the original full `--epochs 200` and signed settings. An intentional rewind to an older completed-epoch checkpoint can append repeated epoch numbers; do not interpret that history as uninterrupted training.
- Rolling `checkpoints/emergency/step-latest.ckpt` files are diagnostic snapshots, not supported training-resume points. After a crash, work since the latest completed epoch may need to be repeated.
- Four-GPU NCCL behavior, full-dataset memory, runtime and long-run convergence must still be checked on the receiving supercomputer. Local small tests do not establish 200-epoch model convergence or absence of spikes.
- This audit does not resolve the separately investigated triplet-coordinate higher-derivative issue, nor establish molecular-dynamics suitability. Nonfinite guards are useful detection, not proof that every finite derivative or large update is acceptable.
- Joint protocol changes and a newly filtered split do not isolate why training improves. Use controlled experiments and matched evaluation sets for scientific comparisons.

No job was submitted and no remote training state was queried as part of this audit. A site-specific resource allocation and launcher remain separate work.
